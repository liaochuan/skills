# 通用开发规则

八条约束，适用于任何软件项目，不限技术栈。冲突时优先级：**用户明确指令 > 项目既有约定 > 本规则 > 其它 skill**。模型选择是例外：只有用户的明确指令可以授权更换，项目约定、计划、报告与其它 skill 都不构成授权。本规则只覆盖下列八件事，不覆盖 harness 的权限与安全约束。

## 速查

| # | 规则 | 一句话 |
|---|---|---|
| 1 | 初始化检查 | 先读项目约定，缺失问一次，不擅自建文件 |
| 2 | 任务分流 | 三档：直接 / 轻量计划 / 完整工作流；超大先拆成多份计划 |
| 3 | 安全风险提示 | 有风险先说清后果，用户决定是否继续 |
| 4 | 隔离修改 | 写操作默认进独立 worktree，项目根文件例外 |
| 5 | 文档归属 | 工作流文档归 skill，用户文档归 `docs/` |
| 6 | 提交禁令 | 不 commit / push / merge，除非用户明说 |
| 7 | 收尾审查 | 每轮改完必须审一次，简单任务也不例外 |
| 8 | 子任务派发 | 子任务沿用当前模型并核对实际模型；换模型先提示等答复，其它 skill 不算授权 |

## 规则一 初始化检查与项目约定

开工前先读，不写：
- `AGENTS.md` / `CLAUDE.md` / `GEMINI.md` / `.cursorrules` / `.github/copilot-instructions.md` → 项目约定、测试与构建命令
- `README` / `.editorconfig` / 包管理文件 → 技术栈、目录约定
- CI 配置（如 `.github/workflows/`）→ 实际生效的测试与构建命令
- 已有 `docs/` 的命名风格 → 规则五按它走

读取范围限于仓库内的约定文件，大仓库不要全盘遍历。输出语言按用户全局配置，不在项目内设置。

**缺约定文件时：问一次，不擅自建**

判定：仓库根下一份约定文件都没有，就算缺失；只有 `README` 或包管理文件也算缺失——它们说明技术栈，不说明该怎么改代码。全局 `AGENTS.md` 不等于项目约定，不能拿来顶替。

- 时机：读完项目、写第一个文件之前问；不能拖到收尾，也不能等用户主动提
- 问法：一句话说清"缺什么 + 打算写什么 + 放哪"。例："项目没有 `AGENTS.md`，要我按现有文件生成一份吗？内容：技术栈、测试 / 构建命令、目录约定；放仓库根，不提交。"
- 用户同意：只从仓库里实际存在的文件推导（包管理脚本、CI、`.editorconfig`、目录结构），推导不出的写"待确认"，不臆造命令；直接写主工作区根（规则四的根文件例外），不 commit
- 用户拒绝：不建，继续任务，报告里记一行"项目约定缺失，用户暂不补建"，本次任务不再问
- 用户未答复：不阻塞任务，按"不补建"继续，报告里注明；下次任务可再问一次
- 禁止：自动创建、把全局约定复制进项目、改语言配置

## 规则二 任务分流

**任一条件命中即升级，不确定就升级。**

| 档位 | 判据 | 路径 |
|---|---|---|
| 直接执行 | 单点改动；不涉及数据结构、对外契约、跨模块调用；无方案分歧 | 规则四 + 规则七自审 |
| 轻量计划 | 多文件但路径明确；无方案权衡 | `writing-plans` 出计划 → `executing-plans`（或本会话内执行），进度写 ledger |
| 完整工作流 | 需求不清、有方案权衡、涉数据结构或对外契约、跨模块或跨服务 | `brainstorming` → `writing-plans` → `executing-plans` |

- **bug 一律先走 `systematic-debugging` 定位根因**，再按上表定档；"明确的 bug"不等于可以直接改。
- **规模也是升级条件**：预估会跨越一次上下文压缩、计划任务数超过约 10 个，或包含 ≥2 个可独立交付的子系统，命中任一即按"完整工作流"处理。拆分粒度是**计划**而非步骤：每份子计划独立可交付、可测试、能单独执行并拥有自己的进度文件（ledger）；另写一份索引，锁定子计划顺序、共享接口与全局约束，子计划只引用不重复定义。
- 文件数只作参考，不作判据；判的是任务数与交付边界。
- 派发子任务（subagent / 后台任务）时按规则八处理模型选择，不自行更换。
- **阶段切换时重读本规则**：从只读分析转入写操作、构建、审查或派发子任务时，重新判断档位与规则八；开场"纯咨询"的判断不延续到实现阶段。
- 执行中变复杂或变大：停下补计划或拆分，不要边写边规划。
- **落盘是执行前置条件**：进入执行前，设计、计划（含拆分索引）必须已写入文件；每个任务开始前从文件重读，不凭记忆；进度与偏离写进 ledger。
- 用户要求跳过：说明风险后照办，并在报告中标注"用户要求跳过工作流"。

## 规则三 安全风险提示（用户决策）

**任何新增需求或改动，先判断是否引入新的攻击面；有风险就明确提示并说清后果，由用户决定是否继续。**

三个必须评估的时机：
1. 需求 / 方案确定前 —— 先于任何实现
2. 改动触及信任边界时 —— 外部输入、认证授权、文件、网络、依赖、配置
3. 收尾审查时 —— 规则七必查项

判定清单（命中任一即算风险；拿不准按有风险处理）：
- 认证与会话：可绕过登录、token 无过期或泄露、会话固定
- 授权与越权：水平 / 垂直越权、IDOR、只在前端隐藏入口而服务端不校验
- 输入与注入：SQL / 命令 / 模板 / 日志注入、XSS、SSRF、反序列化、路径遍历
- 数据保护：敏感字段明文落库或进日志、密钥硬编码、传输未加密、错误信息暴露内部细节
- 文件与上传：类型、大小、落盘路径未校验，写入可执行目录，解压穿越
- 资源与可用性：无速率限制、可放大请求、无超时、可被枚举
- 依赖与配置：引入已知漏洞版本、默认口令、调试开关或 CORS 全开

提示格式（五项缺一不可）：

| 项 | 内容 |
|---|---|
| 等级 | 高 / 中 / 低，按可利用性与影响面判断 |
| 风险点 | 具体到 `文件:行` 或设计位置，不写泛泛的"有安全隐患" |
| 攻击路径 | 谁、从哪一步、需要什么前提才能利用 |
| 影响 | 数据、权限、可用性、合规后果，以及可能连带的其他问题 |
| 缓解方案 | 推荐做法与成本；成本高时给替代方案 |

- 提示必须在动手之前给出，不能写在事后报告里；用户答复前**不开始实现**。
- 用户选择继续：按原方案执行，报告中标注"用户已知悉风险并要求继续"。
- 用户选择调整：按缓解方案改，改完重新评估一遍。
- 用户沉默、"你看着办"、"先做着看"都不构成继续的授权。
- 用户暂时联系不上时，只做只读定位和方案草稿，不落地实现；等有答复再继续。
- 确认有风险的任务至少按规则二的"轻量计划"档；涉及认证、授权、数据外泄的按"完整工作流"。

## 规则四 默认在 worktree 中修改

**除规则一补建的项目约定文件、项目级根文件与回流脚本外，任何写文件的操作都在独立 worktree 里进行。** 你无法知道外部是否还开着别的窗口，所以隔离是默认行为，不是可选项，也不需要先判断「有没有并发」。

1. 建：`git worktree add --detach <worktree 路径> <base>`，默认 `<仓库根>/.worktree/<task>`；`<base>` 取当前 `HEAD` 并记住；任务名用简短 ASCII（如 `task-20261023-1`），不要复用（同名 patch 会被静默覆盖）
2. 路径选择：`<仓库根>` 用 `git rev-parse --show-toplevel` 求。默认建在仓库根之下（`.worktree/<task>`），建之前先把 `.worktree/` 追加到 `.git/info/exclude`（只影响本地，不动 tracked 的 `.gitignore`），避免 `git status` 噪音与误提交。仓库内的副本可能被递归源码/测试 glob（ktlint、detekt、pytest、`node --test` 等）或 IDE 索引扫到，因此跑测试用显式路径（见第 3 条）；若项目属于这类场景且沙箱允许，可改用仓库外路径（如 `../.worktrees/<repo>/<task>`），但须先取得用户同意并在报告中注明。其余情况不得建到父目录或仓库根之外
3. 建完立即写任务元数据（见下）；之后所有读写、测试、导出 patch 都在该目录内执行；跑测试用显式路径，不在主工作区跑全量 glob
4. 只改本次任务范围内的文件，不顺手改无关代码
5. worktree 内可 `git add -N .` 让新增文件进入 diff（只影响该 worktree 的 index）；**禁止**在主工作区执行 `git add`
6. 结束前导出（`<repo>` = 主工作区绝对路径）：

```bash
mkdir -p "<repo>/.git/agent-patches"
git diff --binary "HEAD" "--output=<repo>/.git/agent-patches/<task>.patch"
```

   - 用 `--output`，不要用 `>`：Windows PowerShell 5.1 的 `>` 会写成 UTF-16LE，`git apply` 直接报 `No valid patches in input`
   - 从 worktree 里拼路径时注意 `.git` 是文件、不是目录；求稳可用 `git -C "<repo>" rev-parse --absolute-git-dir`
7. 不 commit、不 push、不合并、不自行清理 worktree

**建不出来时**

| 情况 | 处理 |
|---|---|
| 项目不是 git 仓库 | 降级直接改，报告注明"未隔离" |
| 尚无首次提交（没有可用的 `HEAD`） | 降级直接改，但先说明原因并取得同意 |
| 仓库内路径不可用，或递归 glob / IDE 索引冲突 | 停下报告原因；经用户同意且沙箱允许后，改用仓库外路径（如 `../.worktrees/<repo>/<task>`） |
| 目标路径已存在 | 换任务名（追加 `-2`），不复用、不删除已有目录 |
| `git worktree add` 失败（权限 / 磁盘 / 路径过长） | 停下报告原因，不擅自降级为直接改；用户同意后才降级 |

**任务元数据**（上下文丢了也能续）——建完 worktree 立即写 `<repo>/.git/agent-patches/<task>.json`：

```json
{"task":"task-20261023-1","base":"<建 worktree 时的 HEAD>","scope":"一句话说明改什么","worktree":"<绝对路径>"}
```

- `base` 用建 worktree 时的 `HEAD`，不要到回流时再取"当前 HEAD"
- 回流显式带上：`merge-back.mjs --repo <项目> --base <base> --task <task>`
- 一批 patch 必须同 base；base 不同就分批回流，不要混在一次 `--all` 里

**多任务与子 agent**

- 同一批任务从**同一个 base** 派生；父任务先定 base，再派子任务
- 每个任务、每个子 agent 各自一个 worktree，目录名带任务名；子 agent 只写自己的目录
- 禁止跨 worktree 操作：不 `git add` 别人的目录、不删除别人的 worktree、不替别人回流
- 回流由主 agent 串行执行（脚本会加锁）；子 agent 只导出 patch 并报告路径

**worktree 生命周期**

- 放弃、失败、用户取消：保留 worktree，报告路径与原因，不回流、不删除
- 清理前提：patch 已成功回流并改名 `.applied`，或用户明确说丢弃
- 清理顺序：确认回流 → `git worktree remove <路径>` → `git worktree prune`；只删自己建的路径
- 还没导出就被要求清理：先导出 patch 并确认，再删

**项目根文件例外**：`AGENTS.md`、`CLAUDE.md`、`.gitignore` 这类项目级根文件直接写主工作区根，不建在 worktree 里、不走 patch 回流；否则主工作区看不到，后续会话也读不到。

回流在主工作区串行执行（`<skill 目录>` 是本 skill 所在目录，由 harness 提供）：

```bash
node "<skill 目录>/scripts/merge-back.mjs" --repo <项目> --base <base> --task <task> [--task <task> ...]
node "<skill 目录>/scripts/merge-back.mjs" --repo <项目> --base <base> --all
```

- 退出码 `0` 干净 / `1` 存在冲突 / `2` 失败：参数、环境或补丁问题时不改动主工作区，非预期异常同样归为 `2`，但中途 I/O 失败可能已写入部分文件，需自行看 `git status`
- 多个窗口同时回流时由脚本加锁排队，默认等待 30 秒后报错；持锁进程已退出会立即接管，锁里没有 pid 时超过 10 分钟未更新也会接管
- agent 之间撞同一段：主工作区该文件保持不动，`git apply --3way` 的整合结果（**含 `<<<<<<<` 冲突标记**，不是干净的 agent 版本）另存为 `<file>.theirs`；这是新增的未跟踪文件，取完内容记得删
- agent 撞你未提交的改动：直接在你工作区的文件里写冲突标记，由你解决
- 脚本不创建 commit、不改 index，结果天然是未提交状态；**成功后 patch 改名为 `<task>.patch.applied`**，`--all` 不会重复合入；冲突或失败时保留原文件名

收尾：在主工作区跑测试、人工过 diff；清理按上面的生命周期执行，不留 untracked 噪音。

**例外**：用户明确要求直接在主工作区修改时照办，并在报告中说明未隔离；项目不是 git 仓库或尚无首次提交时同样降级为直接修改（见「建不出来时」）。

## 规则五 文档存放与命名

| 类型 | 判据 | 路径 |
|---|---|---|
| 工作流文档 | 由 skill 流程产生（设计、计划、审查记录） | 该 skill 声明的默认路径，不改写 |
| 拆分索引 | 一个任务拆成多份计划时 | 与子计划同目录，命名 `<feature>-index.md` |
| 用户要求文档 | 用户主动要求写某份文档 | 项目根 `docs/`（规则四下即该 worktree 的 `docs/`，回流后出现在主工作区） |

- 命名：**项目既有约定优先**；无约定时用简洁中文名 + `-` 分隔，如 `docs/部署手册-生产环境.md`
- 内容默认中文；代码、路径、API 字段、术语保持原文
- 工作流文档（设计、计划、审查记录）随 patch 回流入主工作区以便续接，但不属于交付物：报告里点名哪些是工作流产物，用户提交前自行决定保留或删除
- 用户指定路径或命名时照办，报告中注明
- 审查结论默认不落盘，直接回复；用户要求归档时才写文档

## 规则六 Git 提交禁令

**默认只读。**

- 禁止：`commit`、`push`、`merge`、`tag`、`git add` 后提交、任何脚本或 hook 代提交；同样禁止 `reset --hard`、`checkout -- <path>`、`restore`、`clean -fdx`、`stash drop/clear`、`filter-branch` 这类会毁掉工作区改动的操作
- 允许：`status`、`diff`、`log`、`branch`（查看）、`worktree`（按规则四创建与查看）
- 默认**不执行 `git add`**：暂存区是用户的状态，只在其明确要求时改动；规则四中 worktree 内的 `git add -N` 不影响主仓库 index
- 不主动问"要不要提交"，可提示"改动已保存，请自行检查后提交"
- 唯一例外：用户**明确**要求提交（含 "commit" 或给出提交信息）→ 先确认文件清单与提交信息，再执行
- 用户沉默、未回复、"你看着办"均不构成同意

## 规则七 收尾代码审查

**每轮修改结束都必须审查一次，并先于"完成"的结论。** 审的是回流到主工作区之后的合并结果，不是 worktree 里的中间态。

| 档位 | 审查方式 |
|---|---|
| 直接执行 | 作者自审：`git diff` 逐块读 |
| 轻量计划 / 完整工作流 | 独立 subagent 审查（`requesting-code-review`）；不可用时自审并声明局限 |

必查项：
- 需求覆盖：每条要求都能指到具体改动
- 边界与错误路径：空值、超时、并发、幂等、失败回滚
- 界面类改动另查：加载 / 空 / 错误态，键盘操作与可访问性
- 安全：本次改动是否新增攻击面（按规则三清单复核）
- 回归风险：调用方、对外契约、数据迁移、配置默认值
- 测试：改动是否有对应用例，失败用例是否真跑过
- 卫生：调试痕迹、临时文件、硬编码密钥、无关格式化噪音

一次回流多个 patch 时另查：
- 逐个 patch 核对改动是否都进了 diff，没进的说明原因
- 冲突文件与 `<file>.theirs` 是否已处理：`.theirs` 是未跟踪文件，容易漏删、误提交

输出格式：结论（通过 / 阻塞 / 建议）+ `文件:行` + 依据。**禁止**只写"看起来没问题""已验证"。
审查发现问题 → 修复 → 重新验证，最多 2 轮；仍不通过则停下报告，不要边改边宣布完成。

## 规则八 子任务派发不擅自换模型

**派发子任务时沿用当前会话的模型。要换，先说明理由，等用户答复后再派发。**

模型决定成本与质量，成本由用户承担，选择权也在用户。

- 默认写法：不传 `model` / 变体参数（遵循 harness 工具约束，工具说明禁止时不得传）。但"不传"不等于"不用核对"：派发后必须确认子会话实际使用的模型
- **核对方式**：用 harness 提供的会话信息查看子会话 `model`。核对不了就按"未确认"处理，在报告中写明并请用户决定是否接受，不得默认它等于当前会话模型
- **不一致即停**：子会话实际模型与当前会话不同、且用户没有明确批准 → 立即停止向该子会话追加提示，报告差异并等用户决定；不得继续沿用，也不得用"已经跑起来了"当理由
- **其它 skill 不是用户**：`executing-plans`、`subagent-driven-development` 等要求"最终审查用最强模型""必须显式指定 model"时，那只是方法建议；先按本规则提示并等答复。harness 工具禁止传 `model` 时，不得为了满足其它 skill 而违反工具约束
- 确有必要更换（需要更强推理、需要更长上下文、当前模型不可用、成本明显不合理）→ 在**派发之前**给出提示，等用户答复后再动手
- 用户沉默、"你看着办"、"挑个合适的"都不构成更换授权；仍须先提示后更换
- **只有用户明确指定或确认过的模型才算授权**。用户指定某模型时按指定值传，不得自行替换；agent 自己写进计划、报告或 ledger 的模型，按"未授权更换"处理
- 一次批准只覆盖当次列出的子任务与模型；新增子任务、换模型或换变体都要重新问
- 一批子任务用同一模型；确需混用，一次性说明每个子任务用哪个模型、为什么
- 子任务内部再派发同样适用；不得把"要不要换模型"下放给子任务自行决定
- **报告留痕**：报告中列出每个子任务的实际模型；未记录视为未授权

提示格式（四项缺一不可）：

| 项 | 内容 |
|---|---|
| 模型变化 | 现模型 → 目标模型（写具体模型名，不写"更强的一个"） |
| 理由 | 触发点：推理强度 / 上下文长度 / 可用性 / 成本，须对应当前任务的具体困难 |
| 代价 | 费用、速度、质量风险各会怎么变 |
| 影响范围 | 哪几个子任务，是否影响已产出的结果 |

- 换模型不改变规则七：审查仍要独立进行，不因为"换了更强的模型"就免审。

## 常见借口（都站不住）

| 借口 | 现实 |
|---|---|
| "用户催得急，先写代码" | 返工成本高于先规划再动手 |
| "这个 bug 很明确，直接改" | 没定位根因的"明确"通常是猜的 |
| "初始化检查走个形式" | 检查是为了拿到测试命令和约定，走了等于没做 |
| "这个风险很小，不值得打断用户" | 值不值得由用户判断，不由你判断 |
| "先实现，最后一起说风险" | 提示必须先于实现；事后说等于风险已经落地 |
| "内部系统不用考虑安全" | 内部系统同样有越权和数据泄露，且常是攻击跳板 |
| "顺手 commit 一下，反正改完了" | 改完 ≠ 用户同意；提交由用户发起 |
| "审查我自己心里过了一遍" | 没有 `文件:行` 依据的审查不算审查 |
| "改动很小，不用审查" | 小改动同样会引入回归；自审成本只有一次 `git diff` |
| "任务很清楚，不用拆" | 清楚不等于一次装得下；体量本身就是升级条件 |
| "文件拆开了就不会漂移" | 防漂移靠 spec + plan + ledger；拆得不好只是把上下文丢失换成接口漂移 |
| "都在同一个目录改，反正文件不一样" | 看不到外部窗口，隔离不能靠判断，只能靠默认执行 |
| "建到仓库外更干净，测试不会扫到" | 只有递归 glob / IDE 索引确实冲突且用户同意时才用；默认仍守住仓库根 |
| "只有我一个人在改，不用建 worktree" | 是否还有别的窗口不由你判断，统一走 worktree 成本只有几秒 |
| "先 commit 再合并更省事" | 提交由用户发起，回流不需要 commit |
| "项目太小，不用 AGENTS.md" | 约定越少越容易写在几句话里；缺就问一次，成本一句话 |
| "用户没提，说明不想要" | 缺约定文件才要问；建不建由用户决定，不由你替他否决 |
| "先把 AGENTS.md 建在 worktree 里，回流后自然出现" | 主工作区看不到，后续会话也读不到；根文件直接写主工作区 |
| "base 用当前 HEAD 就行" | base 漂移会让回流误判冲突；用建 worktree 时记下的那个 |
| "这是前端/脚本任务，规则不适用" | 八条规则与技术栈无关，按任务性质分流即可 |
| "子任务用便宜的模型更省" | 省不省由用户权衡；换模型前必须先提示 |
| "换个更强的模型结果更好，不用问" | 效果好不是授权；擅自更换让成本与质量都不可预期 |
| "其它 skill 要求用最强模型" | skill 不是用户；方法论不能替用户决定成本 |
| "只是审查，用强模型更稳" | 稳不稳由用户权衡；未授权就是未授权 |
| "计划 / 报告里已经写了这个模型" | 自己写的不算授权；只有用户明确指定或确认才算 |
| "子会话已经跑起来了，接着用吧" | 继续追加提示就是扩大未授权调用；先停再问 |
| "用户说过'你看着办'" | 那是对任务做法的授权，不是对模型选择的授权 |

## Red Flags —— 出现即停

- 用"这是个简单任务"解释为什么跳过审查
- 结论里出现"应该没问题""大概""已验证"但没给命令输出
- 识别到安全风险却先写代码，或只在报告末尾补一句
- 用户还没答复风险提示就开始实现
- 把"用户没提安全"当作不需要评估
- 准备执行 `git add` / `commit` 而用户没提过
- 在项目根目录新建 `AGENTS.md` 或改语言设置
- 还没导出 patch 就清理 worktree，或在主工作区执行 `git add`
- 没建 worktree 就开始写文件
- 把 worktree 建到仓库根之外（父目录、`../.worktrees/` 等），却没有递归 glob / 索引冲突理由或用户同意
- 计划已超过约 10 个任务仍未拆分，或拆分时没先固定共享接口与全局约束
- 凭记忆接着做上一个任务，没回读计划文件
- 派发子任务时传了与当前会话不同的 `model`，却没先提示
- 以"更快 / 更省 / 更强"为由自行换模型，只在事后报告里补一句
- 用"其它 skill 要求最强模型 / 必须显式指定 model"解释换模型
- 派发后不核对子会话 model，或发现不一致还继续追加提示
- 把 agent 自己写进计划 / 报告 / ledger 的模型当成用户授权
- 用省略 `model` 的方式"顺其自然"换模型，事后不核对、不报告
- 缺约定文件却直接开工，一句都没问；或用户拒绝后还反复追问
- 把 `AGENTS.md` 这类根文件建在 worktree 里
- 建 worktree 没写元数据，或回流时不传 `--base`
- 跨 worktree 操作：替别人 `git add`、删别人的 worktree、替别人回流
- 因为"不是后端项目"而跳过本规则

## 示例：复杂任务

用户："帮我实现用户权限管理模块，前端要有角色分配页面，后端要提供权限校验接口"

1. 规则一：读 `AGENTS.md`，拿到测试命令与分层约定；缺失则问一次是否补建
2. 规则二：涉及数据结构与对外契约 → 完整工作流
3. 规则三：识别到越权与权限校验缺失风险 → 给出等级、攻击路径、影响与缓解方案 → 用户确认后再动手
4. 规则四：`git worktree add --detach .worktree/rbac HEAD`，写任务元数据（`base` = 当前 `HEAD`）
5. `brainstorming` 出设计 → `writing-plans` 出计划 → `executing-plans` 执行
6. 规则四：导出 patch，用 `merge-back.mjs --base <base>` 回流到主工作区
7. 规则七：独立 subagent 审查合并后的 diff（派发按规则八：不擅自换模型，派发后核对子会话实际 model）→ 发现失效角色未覆盖 → 修复 → 复测
8. 报告：改动摘要 + 安全提示记录 + 审查结论；**不提交**

纯前端、脚本、纯文档任务走同一套流程，只是规则七的必查项按领域取用。
